# 树莓派 CM5 开源轻量 AI 模型选型报告

- 硬件基线：Raspberry Pi Compute Module 5，4GB RAM / 32GB eMMC / 官方 IO 载板，纯 CPU（无 GPU/NPU 加速）
- 软件基线：64 位 Linux（aarch64），已自编译 llama.cpp，已跑通 Qwen3-VL-2B Q4_K_M，已有 `/picam/shot`（8093）服务端抓图
- 调研日期：**2026-10-31**（所有链接均为当日访问）
- 事实标注：**【实测】** 本机/公开实测数据；**【事实】** 官方文档或模型卡明确写明；**【推断】** 基于公开数据的合理推算；**【待确认】** 必须在本机跑过才能定论

---

## 0. 结论先行

### 0.1 首选组合

**A+B 混合：Qwen3-VL-2B-Instruct（Q4_K_M，复用现有 llama.cpp）负责场景理解 / VQA / 空间关系；RapidOCR + PP-OCRv6_small（ONNX）负责中文 OCR；Kokoro-82M-v1.1-zh（sherpa-onnx int8）负责离线中文播报。**

理由：

1. Qwen3-VL-2B 是当前 4GB 档位里**唯一在本机被完整验证**的多模态方案：文字约 10.2 tok/s、640×480 单图约 15 秒、常驻 RSS 约 2.96GB，运行稳定、无降频【实测】。
2. 它的官方能力覆盖“场景识别、中文 OCR、空间关系、VQA”四项：模型卡明确写有 2D/3D grounding 与 32 语种 OCR【事实】。
3. 专用 OCR 在**印刷体中文**上比 2B VLM 更稳、更快、更省内存；PP-OCRv6 官方档位为 tiny 1.5M / small 7.7M / medium 34.5M 参数，且 RapidOCR 已提供 ONNX 版本，aarch64 部署路径最干净【事实】。
4. Kokoro 82M 的 int8 ONNX 约 88MB【第三方】，Apache-2.0，原生中英双语，是当前许可证最干净、体积最小的中文离线 TTS【事实】。
5. 三者都吃现有 `/picam/shot` 的 JPEG，不需要改抓图链路。

**但 4GB 是硬约束**：2.96GB(VLM) + 约 0.5GB(OCR/TTS/服务) ≈ **3.5–3.9GB**，余量不足 0.5GB。落地时必须采用“按需加载 / 串行执行 / 用完释放”的策略，不能三套全部常驻并发。

### 0.2 内存与延迟预算（首屏结论）

| 方案 | 常驻内存（估算/实测） | 端到端延迟 | 覆盖能力 | 结论 |
|---|---|---|---|---|
| A. 单 VLM（Qwen3-VL-2B Q4_K_M） | **2.96GB**【实测】 | 单图约 **15s**【实测】；文字 10.2 tok/s【实测】 | 1/3/4 + 部分 2 | 已验证，可作基线 |
| B. 专用管线（检测+OCR+TTS） | **0.75–1.35GB**【推断】 | 检测 0.14–0.26s（同量级 YOLOv8n 参考值）【第三方实测】+ OCR 0.8–2s【推断】+ TTS 0.3–1s【推断】≈ **1.2–3.5s** | 1(仅限COCO类)+2+5 | 快、省内存，但空间关系弱 |
| A+B 混合（推荐） | 峰值 **3.5–3.9GB**【推断，VLM 部分为实测】 | 文本场景 1–3s；需要 VLM 时 15–16s | 1/2/3/4/5 | 能力最全，需做内存调度 |

### 0.3 主要风险

1. **内存**：4GB 下 VLM + OCR + TTS 全部常驻会触发 swap，延迟抖增；建议 VLM 按需启动或改用更小的 MiniCPM-V 4.7-1B（待实测）。
2. **热**：CM5 持续跑 VLM 需要主动散热；无散热片时长时间推理会降频。
3. **许可证**：Ultralytics YOLO 系（v8/v11/v26）是 AGPL-3.0，商用需企业授权；Piper 现行代码是 GPL-3.0，且中文音色数据集许可证为 Unknown。两者都不建议直接进商用产品。
4. **部署复杂度**：PaddlePaddle 的 aarch64 预编译轮子在本报告未逐版本核对，直接 `pip install paddleocr` 有编译风险【待确认】；优先走 RapidOCR + onnxruntime 的 ONNX 路线。
5. **空间关系可靠性**：2B VLM 的左右/遮挡判断会出错，必须用固定提示词 + 小评测集验收，不能当作安全关键输出。

### 0.4 最优演进候选

**MiniCPM-V 4.7-1B（1.55B，Apache-2.0，GGUF）**：比 Qwen3-VL-2B 少约 0.5B 参数，官方称 Arm 平台可跑【事实】；第三方变更记录显示 llama.cpp b11551 已合入 MiniCPM-V 4.7 支持【第三方】。若本机实测中文 OCR / 空间问答可接受，可替换 Qwen3-VL-2B，预计省 0.8–1.3GB 内存、单图延迟下降 25–40%。**在其未实测前，不替换已验证的 Qwen3-VL-2B。**

## 3. 分能力分级推荐

### 3.1 物品 / 场景识别

- **首选：Qwen3-VL-2B-Instruct（零样本）**
  直接问“画面里有什么、这是什么场景”，无需训练集，能输出物体、场景、动作描述。官方称识别覆盖名人、商品、地标、动植物等【事实】；本机已验证 15 秒/图【实测】。
  提示词建议固定为：`用中文列出画面中的主要物体（最多8个）、场景类型、以及任何明显的危险或异常。`
- **并列首选（速度路径）：YOLOX-Nano + 场景分类**
  若只需要“有人/有车/有屏幕”这类粗粒度结果，用 YOLOX-Nano（Apache-2.0，0.91M）在 640×480 上做 80 类检测，延迟预计 <200ms【推断】；同量级 YOLOv8n 在 Pi5 NCNN 单线程 137.9ms【第三方实测】。检测结果可先给 TTS 播报，再按需调用 VLM。
- **备选：MiniCPM-V 4.7-1B**，待实测；若中文描述质量接近 Qwen3-VL-2B，则用它省内存。
- **不推荐：**
  - SmolVLM-256M/500M：模型卡语言仅 English，中文场景描述不可用【事实】。
  - Moondream2：模型卡未声明中文能力，中文 VQA 风险高【事实】。
  - YOLOv8n/11n/26n 直接进商用产品：AGPL-3.0【事实】。

### 3.2 中文 OCR（印刷体为主，截图/说明书/路牌）

- **首选：RapidOCR + PP-OCRv6_small（ONNX Runtime）**
  理由：Apache-2.0；模型源自 PaddleOCR 官方权重；RapidOCR 已把 PP-OCRv6 的 det/rec tiny/small/medium 全部转成 ONNX 并支持 `onnxruntime`/`mnn`/`openvino`【事实】；aarch64 上只需 `pip install rapidocr onnxruntime`，避开 PaddlePaddle 编译【事实】。
  速度参考：PP-OCRv6_tiny 在 CPU ONNX、2048 分辨率下 317.06ms【论文实测，测试 CPU 未说明】；在 Apple M4 上 tiny 0.96s vs PP-OCRv5_mobile 5.82s【官方】。CM5 预计比 x86 慢 2–4 倍【推断】，small 档单张 640×480 截图预计 0.8–2s【推断】。
- **备选：PP-OCRv6_tiny**（追求速度，接受精度下降；第三方称 tiny 识别准确率 73.5%）【第三方】。
- **备选：PP-OCRv6_medium**（说明书/低质量扫描；内存仍可控，但慢）。
- **备选：PaddleOCR-VL-0.9B**（复杂版面、表格、公式；0.9B VLM，Q4 约 0.6GB，但单页延迟预计 10s+【推断】）。适合“文档模式”，不适合实时路牌。
- **不推荐：**
  - 直接用 Qwen3-VL-2B 做长文本 OCR：能做，但 15s/图且长文本易漏字；专用 OCR 更稳【推断】。
  - Tesseract：印刷体英文可以，中文场景/截图准确率明显弱于 PP-OCR【推断】。
  - Surya：权重 OpenRAIL-M 带营收门槛，且 689M + PyTorch 在 4GB 上偏重【事实】。

### 3.3 空间关系理解（左右、上下、前后、遮挡、相对位置）

- **首选：Qwen3-VL-2B-Instruct**
  官方模型卡明确写有 “Advanced Spatial Perception: judges object positions, viewpoints, and occlusions; stronger 2D grounding and 3D grounding”【事实】。在本报告候选中，它是唯一同时具备官方空间能力声明与本机跑通记录的模型。
  用法：要求模型输出结构化 JSON（`{"objects":[{"name","bbox","position":"left/right/top/bottom","occluded":true/false}]}`），比自由文本更可控。
- **备选：MiniCPM-V 4.7-1B**（待实测其空间问答；官方未在 README 中给出与 Qwen3-VL 同级别的空间声明）。
- **不推荐：纯检测管线做空间关系。**
  YOLOX/YOLO 只能给 bbox，能做“左右/上下”的几何判断，但**无法可靠判断前后、遮挡、深度**；需要深度模型或 VLM。若必须用管线，只能输出“框的相对位置”，不能声称“前后/遮挡”。
- **风险**：2B VLM 的空间判断会幻觉；必须用本项目自己的 20–50 张图做验收，记录左右/遮挡准确率。

### 3.4 图像问答（VQA，中文优先）

- **首选：Qwen3-VL-2B-Instruct**（中文问答已本机验证；15s/图）【实测】。
- **备选：MiniCPM-V 4.7-1B**（更小更快；系列长期覆盖中英，中文质量待实测【推断】）。
- **备选：InternVL3-1B**（llama.cpp 官方支持，1B 级；但许可证表述有冲突，需读仓库 LICENSE）。
- **不推荐：**
  - SmolVLM / Moondream2：中文能力未声明或仅英文【事实】。
  - Qwen2.5-VL-3B：不是不能用，而是 4GB 下内存余量太小，且被 Qwen3-VL-2B 全面替代【推断】。
  - MiniCPM-V 4.5 / 8B 级：4GB 不可行【事实】。

### 3.5 中文语音播报（离线、机器人音色可接受）

- **首选：Kokoro-82M-v1.1-zh + sherpa-onnx（int8 ONNX）**
  Apache-2.0；82M；中英双语、103 音色；int8 模型约 88MB【第三方】；sherpa-onnx 提供 aarch64 预编译二进制与 Python 轮子，且有 `kokoro-multi-lang-v1_1` 中文模型包【事实】。
  预计 RTF 0.2–0.5（CM5）【推断】，首句延迟 0.3–1s【推断】。
- **备选：MeloTTS 中文（MIT，ONNX 163MB）**
  官方明确“CPU real-time inference”“中文支持中英混读”【事实】；sherpa-onnx 已提供 `vits-melo-tts-zh_en` 转换版，163MB、44.1kHz【事实】。音色比 Kokoro 更“播报腔”，适合说明书朗读。
- **备选：CosyVoice2-0.5B**（音质上限较高，Apache-2.0；但 PyTorch + 0.5B，4GB 下与 VLM 难以共存）【推断】。
- **不推荐：**
  - Piper：维护分支 GPL-3.0；`zh_CN-huayan-medium` 的数据集许可证写的是 **Unknown**，商用有风险【事实】。个人/开源项目可用，但不建议进产品。
  - edge-tts：联网云 API，直接违背离线前提【事实】。
  - ChatTTS 等 CC BY-NC 模型：非商用许可【第三方汇总】。

## 4. 两条路线对比：A 单模型 vs B 专用管线

### 4.1 内存预算

| 组成 | A：单 VLM | B：专用管线 | A+B 混合（推荐） |
|---|---|---|---|
| OS + 基础服务 | 0.3–0.5GB【推断】 | 0.3–0.5GB【推断】 | 0.3–0.5GB【推断】 |
| VLM（Qwen3-VL-2B Q4_K_M + mmproj） | **2.96GB**【实测】 | — | 2.96GB（按需加载） |
| OCR（ORT + PP-OCRv6_small） | — | 0.15–0.30GB【推断】 | 0.15–0.30GB |
| 检测（ORT + YOLOX-Nano） | — | 0.05–0.10GB【推断】 | 0.05–0.10GB |
| TTS（Kokoro int8 + ORT） | 0.15–0.25GB【推断】 | 0.15–0.25GB【推断】 | 0.15–0.25GB |
| 摄像头/业务服务 | 0.1–0.2GB【推断】 | 0.1–0.2GB【推断】 | 0.1–0.2GB |
| **合计** | **3.5–3.9GB** | **0.75–1.35GB** | **3.6–4.1GB（全常驻会超）** |

**结论**：4GB 下 A+B 不能“全部常驻”。可行做法：

1. VLM 服务按需启动（收到“描述/问答/空间”请求才拉起，空闲 60s 退出）；OCR/TTS 常驻。
2. 或把 VLM 换成 MiniCPM-V 4.7-1B（预计省 0.8–1.3GB），让三者可常驻【推断，待实测】。
3. llama.cpp 侧限制 `-c 2048`、`-b 512 -ub 512`，减少 KV/cache 占用；关闭不必要的并行 slot。

### 4.2 总延迟估算

| 场景 | A（单 VLM） | B（管线） | 混合 |
|---|---|---|---|
| “画面里有什么” | 15s + TTS 0.3–1s ≈ **15.3–16s**【实测+推断】 | 检测 0.14–0.26s + TTS 0.3–1s ≈ **0.5–1.3s**【第三方+推断】 | 先 YOLOX 快报 0.5–1.3s；需要细节再 VLM 15s |
| “读这段文字” | 15s（且可能漏字）【实测】 | OCR 0.8–2s + TTS 0.3–1s ≈ **1.1–3s**【推断】 | 同 B |
| “左边是什么/被挡住了吗” | **15s**【实测】 | 管线无法可靠回答【事实】 | 15s（必须 VLM） |
| 连续问答（每问一图） | 15s/问 | 1–3s/问 | 视问题路由 |

### 4.3 取舍

| 维度 | A 单 VLM | B 专用管线 |
|---|---|---|
| 能力覆盖 | 1/3/4 强，2 中，5 需另配 | 1 弱（仅 80 类）、2 强、3 弱、4 无、5 强 |
| 内存 | 高（2.96GB） | 低（<1.4GB） |
| 延迟 | 高（15s/图） | 低（1–3s） |
| 可解释性 | 低（自然语言，可能幻觉） | 高（bbox/文本可追溯） |
| 扩展成本 | 换模型即可 | 每类能力单独调参 |
| 适合 | 盲人辅助、开放场景问答 | 读屏、读说明书、实时播报 |

**建议**：以 B 为“常驻快速通道”，A 为“按需深度通道”。这也正好复用现有 8093 抓图服务：先抓一张 640×480，先跑 OCR/检测，需要理解时再把同一张图喂给 VLM。

## 5. 最小可行组合与演进方案

### 阶段 0：保留现状（已完成）

- Qwen3-VL-2B Q4_K_M + llama.cpp + `/picam/shot` 8093。
- 验收：文字 10 tok/s、单图 15s、RSS 2.96GB、短时压测无降频【已实测】。

### 阶段 1：先加 TTS

- 部署 sherpa-onnx aarch64 预编译包 + `kokoro-int8-multi-lang-v1_1`。
- 只做“把 VLM 的中文回答读出来”，不改识别链路。
- 验收：RTF ≤0.5；首句 ≤1s；连续播报 10 分钟无爆音/卡顿。
- 回滚：TTS 独立进程，失败只影响播报，不影响识别。

### 阶段 2：加 OCR 快速通道

- 部署 RapidOCR + PP-OCRv6_small（ONNX Runtime）。
- 新增 `/ocr` 接口：输入 `/picam/shot` 的同一张 JPEG，输出文本行 + bbox。
- 路由规则：用户说“读一下/上面写的什么” → OCR；说“这是什么/左边是谁” → VLM。
- 验收：20 张本项目场景图（截图/说明书/路牌各若干）字符准确率 ≥95%（印刷体）；单张 ≤3s；RSS 增量 ≤300MB。
- 回滚：OCR 服务独立，VLM 不受影响。

### 阶段 3：加检测快筛（可选）

- YOLOX-Nano ONNX（Apache-2.0）或继续用 YOLOv8n 仅作内部基准（不发布）。
- 用途：先判断“有没有人/有没有屏幕/有没有车”，决定是否值得调用 VLM。
- 验收：640×480 单帧 ≤200ms；误检率可接受；不与 OCR 抢线程（`OMP_NUM_THREADS=2` 分配）。
- 回滚：去掉检测，直接走 OCR/VLM。

### 阶段 4：VLM 替换实验（建议做）

- 并行部署 MiniCPM-V 4.7-1B GGUF（llama.cpp b11551+），同一组 30 张图对比：
  - 中文场景描述可读性
  - 左右/遮挡问答准确率
  - 单图延迟、RSS
- 若“准确率不低于 Qwen3-VL-2B 的 90%，延迟低 25% 以上，RSS ≤2.0GB” → 切换为默认 VLM，原模型保留回滚。
- 否则保留 Qwen3-VL-2B。

### 阶段 5：硬件加速（可选，非默认）

| 方案 | 价格 | 能做什么 | 结论 |
|---|---|---|---|
| Raspberry Pi AI HAT+ 13 TOPS（Hailo-8L） | **$70**【事实】 | CNN 检测/分割很快；LLM/VLM 支持有限 | 只加速检测可考虑 |
| AI HAT+ 26 TOPS（Hailo-8） | **$110**【事实】 | 同上，算力更高 | 性价比一般 |
| AI HAT+ 2（Hailo-10H，8GB 板载） | **$130**【事实】 | 面向生成式 AI；官方生态仍在完善 | 观望 |
| Sixfab AI HAT+（DEEPX DX-M1M，25 TOPS） | 第三方 | 官方实测 Pi5 8GB：Qwen3-1.7B TTFT 599ms、4.64 tok/s【事实】 | 对 2B VLM 提升有限，且要改推理栈 |

**判断**：默认不加加速器。现有 CPU 方案已能跑通全部能力；加 HAT 的主要收益是“检测帧率”和“功耗”，不是“让 2B VLM 变快很多”。若要加，优先 AI HAT+ 13 TOPS 做检测卸载，VLM 仍留 CPU【推断】。

## 6. 本机落地验证步骤（可执行命令思路）

> 所有命令在 CM5 上执行；用 `/usr/bin/time -v` 记录 `Maximum resident set size`，用 `vcgencmd` 记录温度/降频。

### 6.1 环境基线

```bash

vcgencmd measure_temp
vcgencmd get_throttled          # 0x0 表示未降频
nproc

```

### 6.2 复测 Qwen3-VL-2B（确认现有基线）

```bash
/usr/bin/time -v llama-server \
  -m /path/Qwen3-VL-2B-Instruct-Q4_K_M.gguf \
  --mmproj /path/mmproj-*.gguf \
  -c 2048 -b 512 -ub 512 -t 4 \
  --host 127.0.0.1 --port 8080
```

记录：

- `Maximum resident set size`（期望 ≈2.9–3.1GB）
- 首字延迟：`curl -o /dev/null -s -w "TTFT=%{time_starttransfer}s total=%{time_total}s\n" ...`
- 单图：用 `curl` 发 OpenAI 兼容 `/v1/chat/completions`，图片用 base64 或 `image_url`
- 稳定性：连续 30 张图，观察 `vcgencmd get_throttled` 与温度

**验收线**：单图 ≤18s；RSS ≤3.1GB；30 张无 OOM/降频。

### 6.3 测试 MiniCPM-V 4.7-1B（替换候选）

记录：单图耗时、RSS、输出质量。建议同一批 30 张图与 Qwen3-VL-2B 盲评（不看模型名，1–5 分）。

**验收线**：RSS ≤2.0GB；单图 ≤12s；中文可读性 ≥Qwen3-VL-2B 的 90%；左右关系 10 题至少 8 题正确（自建小题集）。

### 6.4 测试 PP-OCRv6_small（RapidOCR）

```bash
python3 -m pip install -U rapidocr onnxruntime

from rapidocr import RapidOCR, EngineType, ModelType, OCRVersion
engine = RapidOCR(params={
    "Det.engine_type": EngineType.ONNXRUNTIME,
    "Det.ocr_version": OCRVersion.PPOCRV6,
```

## 8. 信息冲突与处理

1. **InternVL3-1B 许可证冲突**
   - Hugging Face 元数据页显示 `License: apache-2.0`【事实】。
   - 检索到的 README 摘要写 “released under the MIT License”【第三方检索】。
   - **处理**：以仓库根目录 `LICENSE` 文件为准；在选型表中标注“存在冲突”，商用前必须人工核对。若无法确认，优先 Apache-2.0 的 Qwen3-VL-2B / MiniCPM-V 4.7。

2. **PaddleOCR-VL 版本命名**
   - PaddleOCR README 写 “PaddleOCR-VL-1.6 (0.9B)”【事实】；部分文档页仍写 “PaddleOCR-VL-1.5/0.9B”【事实】。
   - **处理**：能力以 0.9B 档为准；下载时锁定具体模型仓库 revision，避免拿到旧版。

3. **MiniCPM-V 4.6 vs 4.7**
   - 4.6 是 1.3B（2026-04 发布）；4.7 是 1B/1.55B（2026-10 发布），官方提供 GGUF【事实】；llama.cpp 支持见第三方变更记录【第三方】。
   - **处理**：新项目直接评估 4.7；4.6 仅作为回退。

4. **Piper “MIT” 的流传**
   - 旧 `rhasspy/piper` 是 MIT 但已归档；维护中的 `OHF-Voice/piper1-gpl` 是 GPL-3.0【事实】。
   - **处理**：商用默认排除 Piper；个人项目可用旧版 MIT 代码，但中文音色数据集许可证仍为 Unknown【事实】。

5. **Qwen3-VL-2B 的量化体积口径**
   - Qualcomm AI Hub 写 Q4_0 GGUF 1.39GB【事实】；第三方实测 Q4_K_M 约 1.0GiB【第三方】。
   - **处理**：差异来自量化方式与是否含 mmproj；以本机实际文件与 RSS 为准【实测】。
