# GitHub提交与主控审查流程

日期：2026年11月2日  
适用任务：AI眼镜离线语音与视觉交流子系统  
建议使用现有仓库：[NuoAug/CM5-AI](https://github.com/NuoAug/CM5-AI)

GitHub用于接收任务、保存代码、提交变更和保存可核验的交付证据。队友负责开发与修复，AI_Eyes主控侧负责范围、接口和代码审查，最终结合目标板与整机结果验收。GitHub不会自动让本聊天持续运行或自动取得仓库写权限。

## 先把任务文件放进仓库

建议在交互仓库建立 `docs/main-control-task/`，完整放入本任务包的四份文件。它们是主控下达的任务与合同，队友可以提出修改建议，但不能自行改掉职责、离线要求或接口语义后声称满足任务。

可以用一个Issue汇总任务入口，标题例如“执行主控下达的离线语音与视觉交流任务”，正文链接四份文件，并用任务书M0—M5说明本次工作范围。Issue是任务入口，不另外建立接力、认领或交接记录。

先用一个文档PR放入任务文件；开发可以继续在自己的分支开展，不必因等待文档审查而停下独立工作。仓库名称含CM5不代表最终硬件已锁定。

## 分支与提交方式

| 项目 | 约定 |
| --- | --- |
| `main` | 经主控审查接受的代码基线，日常开发不直接推入 |
| 开发分支 | 按一项可独立检查的工作划分，例如 `voice/m0-scope-cleanup`、`voice/m1-streaming-audio`、`voice/m2-visual-context` |
| PR | 一个PR解释一个主要问题与结果，尽量可独立检查和回退；不把全部重构、换模型、训练和接口改动挤成一个巨大PR |
| 未完成的工作 | 可提交Draft PR，清楚列未完成项；需要正式审查时转为Ready for review |
| 审查修复 | 在原PR补充提交，逐项说明如何处理意见；审查期间避免改写历史导致意见无法对应 |
| 接口变更 | 在PR中明确字段/语义变化及兼容影响，由主控确认；不能静默升级合同 |

PR把描述、提交、代码差异和检查结果放在同一处，适合提交前审查；Draft PR用于在做的工作。[GitHub PR说明](https://docs.github.com/en/pull-requests/reference/pull-requests)。

建议第一批依次提交：任务文件；M0删除越界实现并保留主控适配入口；M1语音/取消与合同适配；M2照片和会话管理。模型对照、OCR与训练结果继续按任务书阶段提供，不要求每一份实验日志都单独开PR。

## 每个PR必须说明什么

下面内容可直接作为PR描述模板，按实际变化精简，不填没有执行的结果：

```markdown
本次解决的问题与结果

说明实际触发场景、修改前后的行为，以及对应任务书阶段。

本次改动

- 实现、删除或替换了什么。
- 对接口、模型、配置和启动方式的影响。

验证

- 环境与平台：电脑或具体目标板、系统/运行器/模型版本。
- 复现命令与使用的输入。
- 实际结果、失败与日志/报告路径。
- 如涉及性能：样本数、冷/热、首声/总时间、内存口径。

接口与职责检查

- 合同版本及是否改变语义。
- 是否仍有独立引导或空间判断等越界实现。
- 是否包含测试替身；它与真实模式如何区分。

未完成与已知限制

明确未测、未过和外部依赖，不将它们写成已支持。

回退方式

说明代码/配置/模型如何恢复到上一可运行版本。
```

测试报告必须能够关联到代码提交SHA与模型摘要。报告若在后续提交中加入，注明实际被测的代码SHA，不能假定所有报告都测试了PR当前最新提交。

GitHub Actions可用于语法、单元测试、协议样例和回归检查；它通常不能替代麦克风、AEC、真实目标板、热稳态和电池测试。先完成有价值的检查，不因搭建复杂CI拖延小样交付。

## 主控如何审查

1. 队友把PR链接交给项目发起人，发到主控聊天即可启动本轮审查。只有仓库链接时也能看代码，但明确PR或提交更容易确认变更范围。
2. 主控读取PR说明、差异、适用规则、相关实现与测试结果，记录本次审查的完整head SHA。
3. 需要时将该版本拉到独立检查目录，运行适合的本地检查。不会未经核实就执行安装脚本、模型下载、设备采集或服务变更；超出审查需要的操作单独说明。
4. 主控按严重程度给出具体问题、代码位置、触发条件、影响与修复方向。特别检查图片身份、空间结果时效、危险优先级、语音插话、旧结果取消、离线依赖和资源证据。
5. 队友修复后提供最新提交；主控复核变更和相关回归。新提交不能自动继承旧SHA的审查结论。
6. 主控明确给出代码/接口层面的结论，再由具备仓库权限且获得相应授权的人合并。代码通过不等于目标板或整机验收通过。

主控审查结论至少区分：

| 层级 | 能证明什么 |
| --- | --- |
| 代码与协议审查 | 当前提交在所检查范围内是否符合任务和接口，是否有阻碍交付的问题 |
| 独立运行验证 | 该交互版本在明确环境下的功能、质量和资源表现 |
| 目标板验证 | 实际板端的完整交互性能、音频和持续运行表现 |
| 整机联合验收 | 接入真实感知/深度/定位/人体参数后的并行、失效、热与续航表现 |

即使没有发现代码问题，也要说明哪些层级仍未测。不能把“PR已合并”“自动检查全绿”写成“整套眼镜已通过”。

## 模型和运行包怎样交付

代码、配置、接口说明和适量可公开测试样例放仓库。大型权重与离线运行包按许可使用Release附件或可取得的制品地址，配套清单写明文件名、来源、版本、字节数、SHA256及用途。GitHub自动生成的源码ZIP不等于完整离线运行包。[GitHub Release说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

仓库当前为公开状态，只上传适合公开的样例和脱敏日志；密钥、个人录音、身份信息及无权公开的数据不放入公开提交。大文件大小与下载方式按发布时实际限制处理，不把多GB模型塞进普通代码提交。

## 当前接入能力与后续权限

主控目前已验证可以读取这个公开仓库和公开资料。正式审查可以先在主控聊天给出具体意见，队友按意见修复并更新PR。

将审查意见直接写成GitHub Review/评论、创建Issue或合并PR，需要使用已连接的GitHub账号和对应权限，并得到相应操作授权；读取公开代码不代表已经具备写权限。若暂时没有写权限，不影响主控读取代码、给出审查结论和队友继续修复。

本流程未建立自动监控。每次准备好一个PR或修复版本，把链接与提交交给主控即可；如以后需要自动跟踪新提交，再单独设置。
